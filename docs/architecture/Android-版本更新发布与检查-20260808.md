# Android 版本更新发布与检查

## 目标

以轻量方式完成 Android APK 的服务端发布、登录后检查和用户可控升级。更新检查不阻塞登录，网络异常静默跳过。

## 客户端行为

- 客户端只读取服务端单一的“当前最新版本”元数据，不请求或逐级展示中间版本。
- 更新元数据检查强制走网络且服务端返回 `Cache-Control: no-store`，避免缓存导致旧版本提示。
- 应用进入前台时检查一次，覆盖冷启动和返回应用的场景；已弹出的旧版本提示会被更高 `version_code` 替换。
- 账号会话从未登录切换为已登录时立即检查一次，覆盖应用内登录而不重建 Activity 的场景。
- 可选更新提供“立即更新、稍后提醒、忽略此版本”；忽略只针对同一 `version_code`，新版本仍会提示。
- 强制更新不能被忽略。
- 点击更新后会再次读取当前 manifest，以避免下载期间错过刚发布的更高版本；下载后校验服务端提供的 SHA-256，再调用系统安装器。

## 服务端发布

- `server/config/app-update.json` 是发布元数据来源，必须有正确的 `version_code` 和 `version_name`。
- Server 与 Android 联动发布优先使用 `deploy-remote.ps1 -WithBackend -AndroidApk <apk>`。仅发布 Android 时，完成同等的包名、版本、签名、非 debuggable 和 SHA-256 门禁后，可将 APK 与 manifest 上传到服务器临时目录，再由服务器既有 `publish-android-update.sh` 原子发布；不得手工替换正式目录 APK 或把 debug APK 作为产品更新。
- 部署端校验 APK 包名、`versionCode`、`versionName`、非 debuggable 标志及固定 release 签名证书，再计算 SHA-256 并调用 `publish-android-update.sh`。
- 发布脚本持有互斥锁，拒绝同版、降级和残留的异常高版本。新 APK 与 manifest 均落盘校验后，才原子切换 manifest；失败时旧 manifest 与旧 APK 集合保持不变。
- APK 以 `ZhiWuBen-Android-<version_code>.apk` 保存，清理按数值 `version_code` 完成，不依赖文件修改时间。
- 发布通道固定且只能保留当前最新版和紧邻的上一版本；`--retain` 只能为 `2`，更早 APK 与旧固定文件名包会自动清理。
- `version_code` 必须严格递增；即使连续发布多个版本，元数据接口也只返回最后一次成功发布的最高版本。
- 版本化下载地址使发布切换前已经开始升级的用户仍可获取上一版，但客户端不会再收到上一版更新提示。
- 部署健康检查会读取公开 metadata、下载并校验最新版 SHA-256，同时确认服务器最多只有两版且上一版仍可下载；任一检查失败则发布任务失败。

## API

| 路径 | 用途 |
|---|---|
| `GET /api/app-update/android` | 返回当前发布版本和版本化下载 URL；未发布时为 204 |
| `GET /api/app-update/android/apk/{version_code}` | 下载当前或唯一保留的上一版 APK |
| `GET /api/app-update/android/apk` | 兼容旧客户端，下载当前 APK |

## 发布前检查

1. 提升 Android `versionCode`，并使 `versionCode`、`versionName` 与 manifest 保持一致。
2. 生成固定签名的 `release` APK；部署脚本会再次验证其证书指纹和非 debug 标志。
3. 联动发布使用 `-WithBackend -AndroidApk <release.apk>`；Android-only 发布只能上传到临时目录并调用服务器原子发布脚本，不直接写正式下载目录。
4. 发布后访问 metadata、最新 APK 与上一版 APK 地址；确认更早版本地址为 404。
