# GE4 原生流式与 V100 验证

日期：2026-09-15。目标：验证是否能达到腾讯云式实时流式体验（首字快、持续更新、长时间不积压），并在 GE4 不足时转向 V100。

## GE4 原生流式结果

GE4（Windows 7、i5-650、AMD HD 7800）使用 sherpa-ncnn streaming Zipformer 中文 14M，CPU 推理，4 线程。AMD 显卡未参与计算；这不是 Vulkan/ROCm 加速结果。

| 语料 | 首字（客户端） | 更新 | 更新中位间隔 | 延迟 P50 / P95 | 结束排空 | 结果 |
|---|---:|---:|---:|---:|---:|---|
| 25.29 秒项目短句 | 1.08 秒 | 49 | 344 ms | 381 / 847 ms | 约 0.45 秒 | 实时达标，受控短句 CER 约 1.1% |
| 60 秒研学考察 | 0.89 秒 | 121 | 313 ms | 53 / 350 ms | 78 ms | 实时达标，专业词仍有错字 |
| 180 秒项目管理 | 1.81 秒 | 336 | 约 400 ms | 387 / 1043 ms | 约 0.5 秒 | 无持续积压，准确率不够会议生产 |

测试使用 16 kHz 单声道 PCM，按 100 ms 帧实时发送；流式模型按 300 ms 左右更新。180 秒结果的首字受 SSH/进程调度扰动，GE4 端模型本身首段约 0.7 秒。事件原文保存在 `docs/validation/ge4-20260915/` 与 `tmp/ge4-build/`。

## 准确率边界

速度已经接近腾讯云的交互感，但 14M 模型在长会议中会把“周例会、钢筋隐蔽验收、幕墙”等专业词识别错，不能直接作为高准确率会议主链路。输出是可修订增量文本，仍需稳定提交、重叠去重、停顿切分和专业词热词层。

## V100 验证

目标节点为 `DESKTOP-H3OE2CM` / Tailscale `100.89.195.103`，4× Tesla V100-PCIE-32GB，驱动 475.14。已在独立目录 `D:\LS-Project\labs\meetingnotes-stt` 安装 Python 3.11、PyTorch 2.3.1+cu118 和 FunASR 1.2.6，并下载中文在线 Paraformer（约 881 MB）。`torch.cuda.is_available()` 和 V100 设备枚举正常；将 `sentencepiece` 锁定到 0.1.99 后，在线模型首次推理正常。

25.29 秒受控项目语音使用同一 100 ms 帧回放：首字客户端约 0.72 秒，约 300 ms 更新一次，延迟 P50/P95 为 116/400 ms，平均单次 GPU 推理 96 ms，显存峰值约 871 MB，音频结束后排空约 0.13 秒。模型端和网络通道均未持续积压。在线输出采用增量片段并做前后缀去重，最终结果仍需用长会议人工/CER 验收。

本轮没有修改生产路由、没有启用 V100 服务，也没有替换腾讯云兜底。FunASR 的 Windows 原生依赖需要锁定 `sentencepiece==0.1.99`；更长期的生产方案仍建议使用 sherpa-onnx/ONNX Runtime CUDA 或 Linux/WSL CUDA 11 环境，并在长会议、手机 WebSocket 和并发条件下复测。

## 当前决策

1. 工作站 Windows CUDA STT 继续停用，不恢复 `large-v3-turbo` 服务。
2. GE4 流式方案可作为低延迟实验/轻量预览候选，但暂不接入 Android 生产主链路。
3. V100 Paraformer 已通过短样本 GPU 流式验收，是高准确率主链路的优先部署候选；完成长样本准确率、服务化和 Android/WSS 验收前，腾讯云仍是唯一生产兜底。
4. “腾讯云式实时”必须同时满足速度和准确率，不能只看首字延迟。
