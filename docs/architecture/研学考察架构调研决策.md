# MeetingNotesApp 研学考察架构调研决策

> 文档用途：开发过程的架构镜像与决策记录。
>
> 明确边界：Obsidian 仅供开发者查阅，不属于 MeetingNotesApp 的用户功能、移动端能力、服务端接口或同步依赖。

## 已确认决策

1. 顶层会议类型只保留：通用会议、项目管理、研学考察。
2. 研学考察从“报告模板”升级为独立的 Journey 旅程模式。
3. 内容采用三层形态：StageNote 分段笔记、JourneyEdition 总游记、PublishedPost 发布快照。
4. 暂停录音、暂存本段、暂停旅程、完成旅程、发布笔记必须是不同状态和动作。
5. 旅程级图片不设人为张数上限，采用分批导入、缩略图、断点上传、失败重试和存储配额。
6. GPS 近期只做 EXIF 和事件采点，不默认持续后台轨迹；公开时支持位置降精度和删除。
7. Android 采用 Room + 本地文件作为可信来源，WorkManager/Outbox 负责持久同步。
8. 服务端近期采用模块化单体；真实规模证明需要时再迁移 PostgreSQL、引入独立搜索或推荐服务。
9. 社区只消费用户确认后的发布快照，不直接暴露原始音频、精确位置和未确认内容。
10. 蓝牙耳机和自研硬件后置，BLE 只作为独立控制面，不侵入 Journey 核心领域。

## 核心实体

`Journey`、`JourneyStage`、`CaptureSession`、`MediaAsset`、`LocationEvidence`、`TranscriptSegment`、`StageDraftVersion`、`JourneyEdition`、`PublishedPost`、`SyncOutbox`。

## 推荐路线

1. P0：回归三类模板和已有补丁。
2. P1：本地 Journey/Stage、多图任务、录音与旅程状态、事件采点。
3. P2：阶段证据提取、阶段稿、人工确认和版本快照。
4. P3：总稿合并、私密云同步和冲突处理。
5. P4：社区发布、搜索、互动、审核、位置和 AI 标识。
6. P5：普通蓝牙验证与自研 BLE 控制设备。

## P1 实施记录（2026-08-05）

### 本批已完成

1. Android Room 数据库升级至 v6：新增 `journeys` 与 `journey_stages`，并提供 5→6 显式迁移、外键级联删除、旅程与会议的一对一约束、阶段序号唯一约束。
2. 新增 `JourneyRepository`：创建旅程和首段、暂存当前段、开始下一段、暂停旅程及继续旅程均以独立状态表达；录音的暂停/继续不改变旅程状态。
3. 录音页仅在用户选择“研学考察”后，通过“更多”菜单显式提供“开始研学旅程”；普通会议不会因模板切换而被自动转换。
4. Siri 录音布局增加一条紧凑的“研学旅程 / 当前段”状态，不增加底部并列操作；“暂存本段、暂停旅程、继续旅程”均收纳在现有溢出菜单。
5. 旅程段暂存的正确顺序为：暂存当前段后不创建空白下一段，用户继续旅程时才创建下一段。

## P2-B 实施记录（2026-08-05）

### 本批已完成

1. Android Room 数据库升级至 v8：新增 `stage_draft_versions`，按“阶段 + 版本号”唯一索引保存 `StageDraftVersion`；阶段删除时草稿版本随外键级联删除。
2. 已暂存阶段可基于该阶段归属的转写、图片及其 GPS/EXIF 线索生成 Markdown 阶段笔记。生成仍复用既有 `LLMEngine.chat`，不会改写整场会议纪要流程。
3. 阶段稿遵循草稿/确认两态：草稿可编辑，确认操作使用条件更新，已确认版本不能再编辑或二次确认；再次生成只新增下一版本，不覆盖历史版本。
4. Siri 录音页仍将次要操作收纳在“更多”菜单：没有阶段稿时生成，有草稿时编辑，确认后查看或生成新版本；状态条仅显示紧凑的“阶段笔记待编辑/已确认”。
5. 在研学旅程已暂存、但下一段尚未开始的间隙，录音、导入音频、导入图片、保存人工文本和保存转写结果都会被阻止，确保每条研学证据都有明确 `journeyStageId`。

- 阶段稿 Prompt 覆盖行程段、实际图片清单和“不得虚构图片编号”约束。
- Kotlin/KSP、Room、Koin 与 Compose 参数链完成编译验证。

### 后续边界

- 尚未实现 `JourneyEdition` 总游记合并、社区发布、私密云同步、搜索推荐、后台 GPS 轨迹或 BLE 设备控制。

## P4-B1 实施记录（2026-08-06）

### 本批已完成

1. 服务端新增账户所有者隔离的 `community_posts` 表，使用 `(user_id, client_snapshot_id)` 唯一约束实现客户端快照上传幂等；相同快照重试返回原记录，内容变化返回 `409`，避免网络超时后重复创建社区内容。
2. 新增私有社区同步接口：`POST /api/account/community/drafts`、`GET /api/account/community/drafts/{id}`、`POST /api/account/community/posts/{id}/publish` 和 `POST /api/account/community/posts/{id}/withdraw`。接口复用账户 Bearer 会话，所有查询与状态变更均校验内容所有权。
3. 服务端状态机固定为 `private_draft -> published -> withdrawn`；已发布内容可重复发布请求，已撤回内容为终态；暂存草稿也可以主动撤回，不能再次发布。
4. 服务端只接受结构化快照字段，拒绝未声明的原始资源字段；独立校验隐私检查、内容/图片权利、正文长度、来源版本和精确经纬度表达式，不接收图片二进制、音频、EXIF 或原始 GPS。
5. 发布时记录 `moderation_status=pending`，但本批不实现公共信息流、搜索、推荐、评论、点赞、举报或审核后台；`published` 仅表示服务端已接受发布状态，公开分发仍属于后续阶段。
6. Android Room 数据库升级至 v11：新增 `community_sync_outbox`，以本地 `PublishedPost.id` 为主键和服务端 `client_snapshot_id`，持久保存目标操作、远端内容 ID、尝试次数、错误和同步状态。
7. WorkManager 按单个发布快照建立顺序任务链；网络超时后使用同一幂等键重试，发布或撤回在正在上传时发起会排到当前任务之后，最终以最新 Outbox 操作为准，不会因不确定响应重新创建内容。
8. 本地完成双重检查并进入 `READY` 后自动同步为服务端私有草稿；用户仍需在现有“更多”菜单或发布预览中显式选择“同步并发布”，本地 `PublishedPost` 审核状态与服务端同步状态分开保存。
9. Siri 录音页不增加社区仪表盘或主操作按钮，只复用原有菜单、预览对话框和紧凑旅程状态条显示等待同步、私有草稿、发布、撤回或失败状态。

## P4-B3 实施记录（2026-08-06）

### 本批已完成

1. 服务端新增独立的社区图片元数据表。发布快照可关联任意数量的图片，没有固定 7 张上限；总容量受每账户 512 MB 配额、单张原图 24 MB 和缩略图 2 MB 的明确约束。
2. 图片先建立幂等资源清单，再分别上传原图和缩略图。每个变体使用 `Content-Range`、分片 SHA-256 与服务端已接收偏移量完成断点续传，网络中断后不会重新上传已确认分片。
3. Android 在本地把已确认行程段附件重新编码为 JPEG 原图与缩略图，上传前移除 EXIF；服务端再次清理 JPEG/PNG/WebP 的 EXIF、XMP、IPTC 与 PNG 文本元数据，禁止精确 GPS 随公开图片泄漏。
4. 发布操作要求关联的每张图片均处于完整状态；社区公开接口仍只在“帖子已发布且审核通过”时提供缩略图或原图，私有草稿、待审核、拒绝和撤回状态均不提供公开媒体链接。
5. Android 信息流卡片只展示首张缩略图和图片数量；笔记详情采用横向图片带呈现全部图片，保持单列阅读和紧凑操作，不添加社区仪表盘或复杂图片管理界面。

## P4-B14 实施记录（2026-08-07）

### 本批已完成

1. 清理器增加跨平台 advisory lock，默认使用数据库同级的 `community-media-maintenance.lock`，也可通过 `--lock-file` 指定；锁覆盖媒体扫描、文件移动和 SQLite 事务，防止两个清理进程或清理与备份/恢复维护窗口同时操作同一目录。锁文件必须位于媒体根目录之外。

3. 新增 `meetingnotes-community-media-cleanup.service/.timer` 和安装脚本。systemd 每日执行一次带随机延迟的 dry-run，使用 `COMMUNITY_WRITE_ENABLED=true` 固定禁止写入；服务没有 `--apply` 参数，定时任务不会移动或删除文件。需要正式清理时，运维人员必须先备份、进入只读窗口并手工执行带 `--apply` 的命令。
4. 新增 `server/scripts/audit_community_media_quarantine.py`，默认按 90 天保留期统计隔离 run、文件数和字节数，并单独给出到期候选聚合值。工具只读、无删除和移动能力，不输出 run 名称、媒体路径、用户标识、正文或哈希明细；缺失目录视为空隔离区，符号链接和异常条目直接失败。
5. 隔离区到期处理采用人工审批：候选 run 需要与清理前数据库/媒体备份配对核对，确认恢复演练和观察期完成后才能另行批准不可逆清除。本阶段不实现 purge API、定时删除或 App 端入口，也不把隔离区纳入社区公开索引。

### 运维步骤

1. 发布后以 root 执行 `bash /opt/meetingnotes-stt/current/scripts/install-community-media-cleanup.sh`，确认 `meetingnotes-community-media-cleanup.timer` 已启用；检查 `systemctl list-timers` 和 `journalctl -u meetingnotes-community-media-cleanup.service`，日志只应包含聚合数量或失败原因。

3. 清理后重新运行 `verify_community_backup.py`，再运行 `audit_community_media_quarantine.py <隔离根> --retention-days 90`。到期候选只进入人工审核队列，不得直接使用 `rm`、`find -delete` 或未审计脚本清除。
