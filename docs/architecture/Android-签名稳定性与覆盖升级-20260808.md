# Android 签名稳定性与覆盖升级

## 结论

Android 覆盖升级同时要求 `applicationId` 和签名证书保持不变。此前不同 Codex 会话/构建环境使用了不同 debug keystore，导致同一个 `com.oa.automation` 在设备上的签名指纹与新 APK 不一致，触发 `INSTALL_FAILED_UPDATE_INCOMPATIBLE`。

会话 `019fca92-19e6-7f01-879a-b8677ef2ee7c` 在用户确认后完成过一次“备份数据、卸载旧包、安装新包、恢复数据”的迁移；会话 `019f5e61-4472-7633-8d1a-50035f1c2466` 随后使用另一把本机 debug key 构建，并执行了保留数据卸载，因此设备当前为 `installed=false`，仍保留旧签名记录和数据。第二个会话没有生成旧证书，只是暴露并触发了两套隐式 debug key 的冲突。

迁移不能恢复旧签名证书；旧 keystore 若不可找回，之后必须以新证书作为唯一签名链路。

## 实施

- `android/app/build.gradle.kts` 现在从 `android/signing.properties`、Gradle properties 或环境变量读取 debug/release 签名。
- `assembleDebug` 和 `assembleRelease` 在打包前分别运行 `verifyDebugSigning` / `verifyReleaseSigning`，输出 SHA-256 指纹但不输出密码。
- 公开证书指纹固定在版本化的 `android/signing-fingerprints.properties`；实际 keystore 与登记指纹不一致时构建直接失败。
- 缺少稳定签名配置或登记指纹时，构建直接失败，不再静默生成无法覆盖升级的 APK。
- `android/signing.properties`、keystore 和密码均不进 Git；仓库只保留 `signing.properties.example`。
- 当前 Android 直链升级渠道的 debug/release 均绑定用户私有目录中的固定正式 keystore，不再依赖可能被 Android 工具重建的默认 debug.keystore；指纹由 Gradle 和 `apksigner` 交叉验证一致。正式 keystore 必须在用户私有目录和受控备份中保管，不能提交仓库。

## 发布检查

1. 所有开发机、CI 和服务器发布机使用同一 release keystore；不要在会话中临时生成新 key。
2. 发布前运行 `cd android; .\\gradlew.bat verifySigningConfig`，保存公开的证书指纹到发布记录，不记录密码。
3. 使用 `assembleRelease` 生成正式 APK，并确认服务端发布清单的 `version_code` 高于已发布版本。
4. 如果设备仍有旧证书包，先找回旧 keystore；找不回时只做一次有备份的迁移，迁移后不再更换证书。

## 验证

- `:app:verifyDebugSigning`：通过。
- `:app:assembleDebug`：通过。
- 当前 debug APK 的 `apksigner` SHA-256 与 Gradle 输出一致。
- `:app:verifyReleaseSigning`：通过；debug/release 指纹均为 `512a5cfb...fe78b77a`。
- `:app:assembleDebug`、`:app:assembleRelease`：均通过。
- 真机 Honor REP-AN00：旧签名包已一次性移除，备份数据恢复成功，release 包启动无 Room/SQLite/AndroidRuntime 错误；debug→release 往返覆盖安装均成功，最终包为 release（非 debuggable）。
