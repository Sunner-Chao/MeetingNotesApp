# 实时会议与文件导入转写链路分离

日期：2026-08-07

## 决策

遵循 `simple and effective` 原则，将实时会议和文件导入拆成两条明确的数据链路：

| 入口 | 转写来源 | 停止或导入后的处理 | 模型设置入口 |
| --- | --- | --- | --- |
| 快速会议 | 录音期间的 WebSocket 实时转写 | 保存实时文本，直接生成会议纪要 | 不显示 |
| 预定会议 | 录音期间的 WebSocket 实时转写 | 保存实时文本，直接生成会议纪要 | 不显示 |
| 文件导入 | 导入的文本或音频文件 | 音频进入云端最终转写，完成后再生成纪要 | 仅文件导入页显示 |
| 研学考察分段录音 | 录音期间的 WebSocket 实时转写 | 保存到当前旅程段，不自动重生成总纪要 | 不显示 |

实时会议不再把录音文件送入 `TranscriptionWorker` 做第二次最终转写。录音文件仍被保留，供回听、导出和问题追溯使用。

## Android 数据流

### 快速会议和预定会议

1. `RecordingSessionController` 在接收流式修订文本时累积可用正文。
2. 流式会话发生重连或服务端会话 ID 变化时，保留上一会话文本并做边界重叠去重。
3. 停止录音后，`RecordingService` 保存录音路径、累计时长和实时转写正文。
4. 普通会议直接调用 `BackgroundTaskScheduler.enqueueReport()`。
5. 如果实时转写没有产生正文，不回退到离线模型，也不生成空纪要；界面明确提示本次未生成纪要。

### 文件导入

1. `RecordingViewModel.importAudioDocument()` 保存导入文件。
2. 仅此入口调用 `BackgroundTaskScheduler.enqueueTranscription()`。
3. 大文件仍使用服务端云端分段转写策略，本地模型不参与。
4. 最终转写完成后，用户可继续生成纪要。

### 研学考察分段

分段录音停止后，实时正文按 `journeyStageId` 保存。每一段不会自动生成完整会议纪要，避免边走边录时反复覆盖总游记；阶段笔记和总游记仍由研学工作流显式生成。

## 来源持久化与导航

`Meeting` 新增 `MeetingOrigin`：

- `QUICK`
- `SCHEDULED`
- `FILE_IMPORT`

Room 数据库从 14 升级到 15。迁移会将旧标题中包含“资料导入”“文件导入”“导入会议”或 `import` 的记录标记为 `FILE_IMPORT`，将旧预定会议标题标记为 `SCHEDULED`。

来源不再依赖当前标题判断，因此用户改名后行为仍保持正确：

- 新文件导入记录统一命名为“文件导入 MM-dd HH:mm”。
- 最近记录中的待完善文件导入会恢复到文件导入页。
- 快速会议和预定会议会恢复到实时录音页。

## UI 收口

- 快速会议 Siri 录音页移除“识别设置”。
- 快速会议实时转录卡移除模型和语言切换。
- 文件导入页保留“识别设置”，用于导入音频的最终转写。
- 文件导入与实时录音仍可互相切换，但重新进入记录时以持久化来源为准。
